# Разбор данных 2026-09-25

Первый разбор реальных данных. Сборка — релиз `0.2.0`, устройство — Samsung
Galaxy S23 (SM-S911B, Android 16). Период — 22.09 16:03 – 25.09 00:32 MSK.

В документе нет координат, номеров телефонов и адресов; где нужна привязка к
месту, указаны только расстояния.

---

## Коротко

- **Сбор работает.** Пассивный слой непрерывен, потерь отсчётов нет, One UI
  приложение не усыпляет. Единственная дыра — 99 минут, когда телефон был
  выключен (села батарея; приложение тут ни при чём, его доля ~1 % разряда).
- **Интенсивные сессии полные.** Все четыре записаны целиком, предыстория 60 с на
  месте. Целевой сценарий пользователя (сессия #4) читается по данным от
  начала до конца.
- **Главная проблема — журнал и метки недоступны.** Они лежат только в Room, и в
  релизной сборке их с компьютера не достать. Проверить геофенсы и задержки
  доставки (§4.4) пока нельзя. Решение — выгрузка в `Documents/Sesame/journal/`
  (§5); реализовано в коде, не проверено на устройстве.
- **Мелкие расхождения с ТЗ:** остановка по таймеру с открытого главного экрана
  записывалась как `request`; фактическая частота пассивных датчиков в разы выше
  запрошенной.
- **Пассивной локации для манёвров во дворе мало** — это ожидаемо по дизайну;
  детали есть только в интенсивной сессии.

## 1. Сбор и покрытие

### Пассивный слой

Акселерометр и барометр непрерывны, `droppedSamples = 0` во всех сутках.
Сервис foreground жив всё время, standby bucket — `EXEMPTED`, приложение в
белом списке deviceidle, все разрешения выданы, включая
`ACCESS_BACKGROUND_LOCATION`, `ACTIVITY_RECOGNITION` и `CALL_PHONE`. То есть риск
§11 «One UI усыпляет приложение» на этих трёх сутках не проявился.

### Единственная дыра: 24.09 01:52 → 03:31 (99 мин)

Телефон был выключен. Загрузка в 03:27 с причиной `reboot,lpm` — старт из режима
зарядки выключенного аппарата, то есть батарея, видимо, села. Сервис поднял
`BootReceiver` в 03:31, примерно через 4 минуты после загрузки.

Запуск сервиса предыдущей загрузки остался в `day.json` без `closedAtMillis`:
процесс умер без чистого завершения. Данные до 01:51:57 при этом опубликованы —
флаш раз в 10 секунд (§5) сработал как задумано.

### Энергопотребление

За 16 часов на батарее приложение потратило ~40 мАч из 4210 мАч общего разряда,
около 1 %. Батарею посадило не оно.

### Фактическая частота пассивных датчиков

| Датчик | Запрошено | Фактически |
|---|---|---|
| Акселерометр | 5 Гц (`requestedDelayUs = 200000`) | median dt 19 мс (~52 Гц), в среднем за сутки 31–41 Гц |
| Барометр | 1 Гц | 5 Гц (22–24.09) |

Вероятная причина — sensor hub Samsung отдаёт максимум из частот всех клиентов
датчика. Объём акселерометра — ~45 МБ gzip в сутки, против ~2 МБ, заложенных
в §4.4. Для хранения некритично (≈0.3 ГБ в неделю при лимите 10 ГБ), но:

- анализ не должен предполагать 5 Гц — только метки времени;
- частоту в манифесте надо читать как **запрошенную**, а не фактическую (§6).

### Пассивная локация

Параметры по умолчанию: `BALANCED`, 120 с, 25 м.

- 25–81 фикс в сутки; median интервал ~2 мин, p90 — 18–55 мин (стоянки, работает
  фильтр смещения).
- Точность: median 22–38 м. Скорость есть только в части строк.
- На эпизод манёвра во дворе приходится 3–4 точки. Для таких манёвров пассивного
  слоя недостаточно, детали есть только в интенсивной сессии.
- Во время интенсивной сессии пассивный клиент тоже получает точные фиксы со
  скоростью: запрос `HIGH_ACCURACY` поднимает всех клиентов.

Акселерометр и гироскоп дают ~200 Гц, а не 400–500 Гц, ориентировочно

### #1 — «Еду домой», 22.09 22:55–23:05, стоп вручную

Первые ~5 минут в машине GNSS так и не дал фикса: точность 30–100 м, скорости

### #2 — «Пешком», 23.09 12:42–12:57, по таймеру

Пешком ~4 минуты, затем езда до 38 км/ч. В последнюю минуту точность

### #3 — «Еду из дома», 24.09 12:32–12:47, по таймеру

Старт на месте, езда с 12:37. С 12:43 GNSS теряется: точность 66–400 м, скорости

### #4 — «Еду домой», 24.09 22:46–23:00, стоп вручную

Целевой сценарий пользователя: заехал во двор, мест нет, выехал, поставил машину
дальше и прошёл пешком, шлагбаум не открывая. Читается полностью:

| Время | Что видно |

| 22:46–22:49 | езда до 40 км/ч |
| 22:49:40–22:50:40 | 1–5 км/ч в ~20 м от финальной точки — заезд во двор |

## 3. Проблемы и что делать

| # | Проблема | Решение | Статус |
|---|---|---|---|
| 1 | Журнал и метки недоступны с компьютера | выгрузка в `Documents/Sesame/journal/` | реализовано в коде, не проверено на устройстве |
| 2 | Таймер с открытого главного экрана пишется как `request` | таймер даёт `timer` | реализовано в коде, не проверено на устройстве |
| 3 | Пассивная частота accel/baro выше запрошенной | задокументировано в §6 | прореживание — вопрос к пользователю |
| 4 | Пассивной локации мало для манёвров | ожидаемо; нужна интенсивная сессия | идея, не решение |
| 5 | Холодный старт GNSS в машине | — | наблюдение, идея |

### 1. Журнал событий и метки лежат только в Room — главное

`LogEvent` (геофенсы, Activity Recognition, Wi-Fi, Bluetooth, звонки, а главное —
пары `eventTime` / `receivedTime`) и `PassageLabel` хранятся только в Room во
внутреннем каталоге приложения. В релизной сборке их не достать: `run-as` нет,
`adb backup` для targetSdk 36 не работает, share sheet выгружает только сессии.

Следствия:

- нельзя проверить, сработал ли геофенс при заезде и выезде и с какой задержкой, —
  а это главный вопрос v0 (§4.4);
- переустановка уносит журнал и разметку, что противоречит духу §7.

**Решение** — выгрузка в `Documents/Sesame/journal/`: события посуточно, метки и
сессии полными снимками; они же попадают в zip «Поделиться непошаренным».
Формат, расписание публикации и поведение после переустановки (файлы с суффиксом
`(1)`) — в §5 ТЗ. Статус: реализовано в коде, не проверено на устройстве.

### 2. `stopReason` при остановке по таймеру

Если главный экран открыт, таймер там же и срабатывает: `HomeViewModel.autoStop`
→ `RecordingSessionController.stop()` → `CollectorService` `ACTION_STOP_SESSION`,
а эта команда записывает `request`. Сессии #2 и #3 закрыты по таймеру через
0.5–0.8 с после `plannedEnd`, но в `session.json` стоит `request`.

**Решение:** остановка по таймеру передаёт `timer` (extra `EXTRA_STOP_REASON` в
команде остановки, по умолчанию `request`). Список значений `stopReason` — в §6
ТЗ. Статус: реализовано в коде, не проверено на устройстве. В уже записанных данных таймер отличается от кнопки
по разнице между временем остановки и `plannedEnd` (меньше секунды — таймер).

### 3. Фактическая частота пассивных датчиков выше запрошенной

Задокументировано в §6. Решение о программном прореживании **не принято**: объём
терпим, а лишняя частота бесплатно отвечает на вопрос §13 «хватит ли пассивной
частоты». Вопрос к пользователю.

### 4. Пассивной локации мало для манёвров во дворе

Ожидаемо по дизайну: в покое `BALANCED` с фильтром смещения и должна молчать.
Для анализа сценариев нужна интенсивная сессия. Идея на будущее — триггер
автозапуска интенсивной сессии; в v0 это явно отклонено (§2), и здесь это только
идея, не решение.

### 5. Холодный старт GNSS в машине

В сессии #1 первые ~5 минут без нормального фикса; в #4 фикс через 20 с. Идея:
держать запрос `HIGH_ACCURACY` заранее вблизи дома, чтобы к подъезду GNSS уже
был «тёплым». Только идея — цена по батарее не оценивалась.

## 4. Как забирать данные

- USB-передача данных на компьютере пользователя не заработала, использовалась
  **беспроводная отладка**: `adb pair` по коду из настроек разработчика, затем
  `adb connect`. Порт подключения отличается от порта сопряжения; если mDNS не
  находит устройство, порт можно найти сканированием.
- В Git Bash нужен `MSYS_NO_PATHCONV=1`, иначе путь на устройстве превратится в
  путь Windows:

  ```bash
  MSYS_NO_PATHCONV=1 adb pull /sdcard/Documents/Sesame
  ```

- 227 МБ по Wi-Fi заняли ~100 с.
